# Implementation Notes - Impact Frontier Homepage Game

Version: 0.2 working notes  
Status: updated after the v3 working prototype

## 1. Build posture

The current direction is no longer a blank design search. There is now a working lead direction:

```text
A bright research homepage with a harbor-front 3D lake economy as the interactive centerpiece.
```

Future agents should refine this direction rather than returning to a lake-in-the-center layout or a full-screen game flow.

The website is not titled "Lake Economy". The visible site title should be **The Impact Frontier**. Lake Economy is the internal name of the playable model/world.

## 2. Preferred stack

Preferred architecture:

- React or Next.js for page structure,
- TypeScript for the game model,
- Three.js or React Three Fiber for the 3D harbor scene,
- SVG, Canvas, or D3 for the frontier chart,
- no backend for MVP,
- no database for MVP.

For fast prototypes, vanilla JavaScript is acceptable if the code remains cleanly separated.

The model should run client-side.

## 3. Code separation

Keep the economic model separate from the visual layer.

Current active implementation map:

- `app/page.tsx` renders `components/lake-economy/LakeEconomyHome.jsx`.
- `LakeEconomyHome.jsx` mounts the interactive runtime from
  `components/lake-economy/runtime.js`.
- The active About, Papers, and Guide panel markup is generated in
  `runtime.js` by `contentForMode(mode)`.
- The active homepage styling is in
  `components/lake-economy/lake-economy.css`.

Agents should not assume a file in `components/` is active just because it has
a plausible name. Before changing user-visible content, search for imports and
call sites, then verify the rendered page. If a duplicate implementation is no
longer active, move it to `archive/` or delete it rather than letting it remain
beside active components.

Suggested production structure:

```text
src/
  game/
    economyTypes.ts
    scenarioTemplates.ts
    generateLakeEconomy.ts
    solveEconomy.ts
    computeFrontier.ts
    scoreRun.ts
  components/
    HarborScene.tsx
    PlayPanel.tsx
    EntityPopup.tsx
    ResultsPanel.tsx
    FrontierChart.tsx
    ResearchPanel.tsx
  app/
    page.tsx
```

The 3D scene should read solved game state. It should not contain economic logic.

The chart should read frontier and result data. It should not solve the economy.

## 4. R model reference

The file `lake_economy_model_prototype.R` is the current tested reference for the game engine.

Implementation agents should port the model logic into the website stack rather than inventing a new economic engine.

The R file defines:

- six-entity economy setup,
- player offers,
- player supply shift,
- other-investor supply,
- issuer demand,
- equilibrium prices and capital quantities,
- lake health and local prosperity outcomes,
- approximate playable frontier calculation.

The R file is not a visual-design spec. Its plotting choices should not be copied unless they fit the website.

## 5. Economic model flow

Use the R model's non-marginal P/K-space clearing structure.

Core quantities:

```text
P: equilibrium capital costs / required returns
K: equilibrium issuer capital
b_share: player offer shares, nonnegative and summing to one
s_player: player supply shifter generated by offers
E_player: player quantity-form supply elasticity
E_other: other-investor quantity-form supply elasticity
PhiS: inverse aggregate supply slope
B: inverse demand slope matrix
```

Supply and demand:

```text
K_player(P,b) = c_player + E_player P + s_player(b)
K_other(P)   = c_other  + E_other P
K_S(P,b)     = c_supply + E_total P + s_player(b)
P_D(K)       = a_demand - B K
P_S(K,b)     = PhiS [K - c_supply - s_player(b)]
```

Clearing:

```text
P_S(K,b) = P_D(K)
```

Solution:

```text
K(b) = solve(PhiS + B, a_demand + PhiS * (c_supply + s_player(b)))
P(b) = a_demand - B * K(b)
```

Then compute:

```text
K_player(b)
K_other(b)
lake outcome
prosperity outcome
blended outcome
player CE or risk-adjusted return
```

## 6. Actual capital definitions

Be precise in the UI.

Do not label the result simply as "actual capital" unless a nearby explanation is present.

Preferred labels:

```text
Actual capital change vs baseline
Total Delta K vs baseline
```

Definition:

```text
Actual capital change = K under current offers - K under equal-offer baseline
```

This is baseline-relative total firm capital after market clearing. It is not the player's direct investment.

A negative value means the firm receives less capital than under the equal-offer baseline. It does not mean the firm disappears.

Where useful, show:

```text
Offer
Total Delta K
Player Delta K
Other investors Delta K
```

This makes it clear that other investors respond and that the player's offer may shift capital away from other firms relative to baseline.

## 7. Determinism

A run of the same lake should be deterministic.

```text
Same lake + same offers = same result
```

Randomness should enter only when generating a new lake.

Use seeded randomness if practical so runs can be reproduced and shared later.

## 8. Scenario templates

Do not fully randomize everything. Start from validated templates and randomize only within safe bounds.

Recommended templates:

1. Feed bottleneck
2. Market access bottleneck
3. Scalable entrepreneur
4. Dirty growth trap

Each template should produce a valid mathematical system.

## 9. Feasibility and safe parameter generation

Parameter generation should avoid broken systems.

Basic requirements:

- no negative baseline firm sizes,
- no impossible final sizes in ordinary play,
- stable supply and demand matrices,
- positive semidefinite or regularized positive definite financial-cost/risk matrix,
- frontier computation should not fail for normal offer vectors,
- final `K` should remain nonnegative in normal play,
- baseline-relative `Delta K` may be negative.

For the MVP, hand-tuned parameter sets are acceptable.

## 10. Frontier computation

The visible website chart should use:

```text
x-axis: expected outcome change
y-axis: risk-adjusted return
```

It is fine to compute internally with CE values or CE loss, but the visible chart should not be drawn as cost versus outcome.

For MVP, a grid search or simple numerical optimization is fine. There are only six entities.

Constraints:

```text
b_n >= 0
sum_n b_n = 100
```

The frontier should be the playable constrained frontier, not a fully unconstrained analytical frontier.

Baseline for gains and losses:

```text
equal offers
```

## 11. Top-level UI structure

The top bar should stay visible.

Target elements:

```text
TPP logo
CSP logo
HSG logo
The Impact Frontier
Papers
Guides
Methods
Play
```

Papers, Guides, and Methods should open large panels above the economy. They should accept ordinary HTML so screenshots, abstracts, links, and guide cards can be added later.

The panels should not blur, darken, or gray out the economy.

## 12. Play panel

The Play panel should be compact and non-blocking:

- left side,
- small enough to keep the world visible,
- no full-screen modal,
- no centered blocking overlay,
- no dark mask,
- no blurred economy.

The economy must remain visible and orbitable while the Play panel is open.

## 13. Step gating

Initial state:

- no goal selected,
- Step 2 greyed out,
- Step 3 greyed out.

Unlock rules:

```text
Step 1 completed -> unlock Step 2
Step 2 completed and Run economy clicked -> unlock Step 3
```

Step 1 is completed when the user clicks a goal button or moves the goal slider.

Step 2 is completed when the user allocates all 100 offer tokens.

Run economy should be disabled until Step 2 is complete.

## 14. Entity popups

Do not show permanent entity detail subpanels in the Play panel.

Use entity popups instead.

Open a popup when the user:

1. clicks the 3D entity,
2. clicks the entity name/link in the offer list.

Close the popup when the user clicks outside it or presses close.

Before a run, show only visible characteristics:

- expected business return,
- risk,
- lake health intensity,
- local prosperity intensity.

After a run, popups may also show:

- offer,
- total capital change versus baseline,
- player capital change versus baseline,
- other-investor capital change versus baseline,
- lake health effect,
- local prosperity effect.

Do not show hidden responsiveness or the exact response matrix at the start.

## 15. Visual scene direction

Use a harbor-front lake economy, not a circular lake-in-the-center layout.

Required scene features:

- water in front,
- non-trivial curved shoreline,
- green land rising gently to the back,
- slightly undulating terrain,
- low-rise town background,
- all six investable entities along the shoreline,
- boats on the water,
- roads, docks, trucks, trees, and ground details,
- other investors visible,
- bright off-white or grey surrounding background.

Avoid:

- yellow/orange background from the Harbor Town reference,
- somber dark-green palette,
- flat white/grey ground under structures,
- skyscraper city aesthetic,
- flashing roof artifacts,
- ambiguous spinning yellow objects.

## 16. Visual offer indicators

Offer changes should be visible in the Play panel and the 3D world.

Use:

- numeric offer bubbles above entities,
- small offer bars beside entities,
- yellow fill increasing to the right as the offer increases.

The offer bar is only a visual representation of offer strength. It should not imply final capital.

## 17. Boats

Include boats that look like harbor or lake boats.

Good direction:

- several small boats,
- simple hulls,
- different colors,
- slow movement if cheap,
- not too much animation.

## 18. Homepage panel content

Papers panel should support:

- Paper 1: The Impact Frontier,
- Paper 2: Shifting the Frontier,
- screenshots or PDF thumbnails,
- links to papers.

Guides panel should support:

- investor guides,
- plain-language summaries,
- links and screenshots.

Methods panel should support:

- short explanation of the offer-clearing-frontier loop,
- technical notes,
- model explanation for interested users.

## 19. MVP scope

A good MVP includes:

- top research-site bar,
- harbor-front 3D economy,
- orbit and zoom controls,
- six investable entities,
- compact Play panel,
- goal choice before offers,
- 100-token offer allocation,
- deterministic Run economy,
- Start fresh,
- New lake,
- entity popups,
- visible offer bars,
- visible distinction between offers and capital changes,
- frontier chart or score,
- Papers and Guides access.
- Starting view facing town from lake
- Lake gets darker and uglier for more negative outcomes
- Entities visually react to more or less investment
- Visual negative effect of less prosperity

## 20. Deferred features

Defer:

- coalition negotiation,
- policy cards,
- stewardship cards,
- borrowing,
- multi-period dynamics,
- stochastic shocks inside repeated runs,
- time evolution of the town,
- density controls,
- advanced finance UI,
- full paper math in the main game flow.

The architecture should leave room for Paper 2 modules later.
